Use cases

These are full sessions run through DARE, stage by stage. The first four use VulnShop, the deliberately vulnerable e-commerce app I teach with; the rest reach beyond the book into APIs, Active Directory, the cloud, the network, and the blue team, because the framework was never limited to web vulnerabilities. Each one follows the same arc: understand the system, break it, watch it get fixed, then see the break from the other side. This library grows over time, so check back.

Use case 01

SQL injection, in the search box

VulnShop's product search takes whatever a shopper types and drops it straight into a database query. No parameterization, no escaping. The vulnerable field is the search box on the homepage, which is about as ordinary as an input field gets, and that's the point.

DDeconstruct

Before any injection happens, the learner needs to be able to explain what a database query actually is and how their search term becomes part of the command sent to the database, rather than staying separate from it. I sketch it as one string: the app's fixed code plus whatever the shopper typed, concatenated together and executed as-is. By the end of this stage the learner should be asking themselves what happens if the text they type stops behaving like text.

AAttack

I type ' OR '1'='1 into the search box and the result set jumps from a handful of matching products to the entire catalog, including items that were never meant to be listed. The learner repeats this on the same target, then moves to an independent target where the injectable field is different, the account settings page instead of search, so copying my exact string does nothing. A learner who understood Deconstruct can explain why the quote character breaks the query. One who didn't can only tell you that the string worked.

RRemediate

The one and only change in the patched version is that the query is now parameterized, the search term is passed as data instead of being pasted into the command. Same search box, same payload, and it now returns zero results, exactly like searching for a product that doesn't exist. That is the correct behavior, and I say so directly.

EExchange

I pull up the request log generated by the learner's own search and let them read it before I explain anything. What jumps out is how plainly the injected syntax sits there in a single log line, quote marks and all, next to a thousand ordinary searches for shoes and phone cases. Most learners expect an attack to look more deliberate from the defender's side. Seeing it as one slightly odd-looking line in a wall of normal traffic is usually the moment this stage is built for.

Use case 02

No rate limiting, on the login form

VulnShop's login form accepts as many attempts as you want to throw at it, no delay, no lockout, no captcha after a threshold. The target is the login form, tested with Burp Suite's Intruder against a list of common passwords.

DDeconstruct

The learner needs to understand what a login request actually is, a small package of credentials sent to a server, and what a tool like Intruder does to it: replaying that package with a different guess in the password field each time, as fast as the server allows. I usually capture one manual login first and show the same request sitting in Burp, so the jump from "one login" to "a thousand automated logins" is visible rather than abstract.

AAttack

I run Intruder against the login form with a common password list and narrate what I'm watching for, a response that's a different length or status code than all the failed attempts around it. The learner repeats the run, then moves to an independent target, the password reset form instead of login, which takes the same unlimited-attempts idea and applies it somewhere they haven't seen it demonstrated. That's what separates recognizing the pattern from replaying a recording.

RRemediate

The single change is a lockout after a small number of failed attempts from the same account. Same password list, same Intruder run, and it now stalls a few attempts in, well short of the real password. I point at exactly where it stops and explain that this is the account protecting itself.

EExchange

The evidence here is loud in a way SQL injection isn't: a burst of failed login attempts from a single source, landing within seconds of each other. I show the learner the raw timing between requests before saying a word. It's usually the first time they've thought about how obviously mechanical automated traffic looks once you're the one watching it arrive.

Use case 03

IDOR, in the order history

VulnShop's order confirmation page loads an order by its ID straight from the URL, and never checks whether the order belongs to whoever is asking. The target is the order history page, where order IDs are sequential integers.

DDeconstruct

Before touching anything, the learner needs to understand what an object reference is, a value in a URL, like an order ID, that points directly at a specific record on the server. I show them a real order URL and ask what they think happens if that number changes. That question is the entire point of this stage, and I don't answer it for them yet.

AAttack

I change the order ID in the URL by one and a different customer's order appears, full name, address, items purchased. The learner repeats it on the same target, then moves to an independent target with a different ID pattern, account settings instead of orders, so they have to recognize that "sequential ID, no ownership check" is the actual vulnerability, not "this one URL."

RRemediate

The one change is a server-side check that the requested order actually belongs to the session asking for it. Same incremented ID, same request, and it now returns a not-found response instead of someone else's data. I make the point that the ID being guessable was never the real problem, the missing check was.

EExchange

The logs show a single session requesting a run of sequential order IDs that don't belong to it, one after another. Laid out in a request log, that pattern is about as subtle as a shopping cart on fire. I ask the learner to describe what they see before I point out what makes it stand out, and by then most of them have already spotted it themselves.

Use case 04

Stored XSS, in a product review

VulnShop lets shoppers leave a written review under any product, and renders that text back to every visitor who views the page without encoding it first. The target is the product review field, and the payoff is a stolen session cookie.

DDeconstruct

The learner needs a working sense of two things: what JavaScript running in someone else's browser can actually do, and what a session cookie is worth to someone who gets hold of it. I sketch the flow as one sentence: whatever gets stored in this field gets rendered back to the next person who loads this page. That sentence is what makes stored XSS click before anyone has written a payload.

AAttack

I post a review containing a script that sends the viewing browser's cookie to a listener I control, then open the product page in a second, victim browser session and watch that cookie arrive. The learner repeats it, then moves to an independent target, a profile bio field instead of a review, so they have to recognize "stored input, rendered unescaped" as the pattern rather than reuse my exact payload.

RRemediate

The one change is that stored input is now encoded before it's rendered back into the page. The same review, posted the same way, now shows up on screen as plain, inert text, angle brackets and all, instead of running as code. I point out that the review still saved successfully, it just isn't allowed to act like a program anymore.

EExchange

The evidence is the listener's own log: a request arriving from the victim's browser, carrying their exact cookie value, timestamped to the second they loaded the product page. I let the learner sit with that before explaining it, because it's usually the first time they've seen their own payload act on a browser that isn't theirs.

Use case 05

Broken object-level authorization, in the mobile API

VulnShop has a mobile app, and behind it a JSON API. GET /api/orders/{id} returns an order by its number. The API checks you are logged in. It never checks the order is yours. This is IDOR grown up: the same missing question, one layer deeper, where most people stop looking.

DDeconstruct

Before touching the API, the learner needs to separate authentication from authorization at the API layer, and see that an id in a URL maps straight to a database row. The holding question is the one the server forgot to ask: it confirmed who you are, but did it confirm the object is yours?

AAttack

I call the endpoint for my own order, then change the id and watch someone else's order come back, items and delivery address included. The learner repeats on their own account, then moves to an endpoint where the id is a UUID they have to discover first, so guessing does nothing. Success is naming the missing ownership check, not just pulling data.

RRemediate

The one change in the patched API is a server-side check that the requested object belongs to the caller. Same request, and now it returns 403. A pentester is supposed to fail here. The 403 is not the tool being blocked, it is the application finally asking the question it should have asked from the start.

EExchange

I open the API logs. A single session requesting a run of ids that plainly are not its own is one of the most obvious patterns a defender will ever see. The learner, who a moment ago was the attacker, can now say exactly what they would alert on, and what they would have done to spread the requests out and stay quiet.

Use case 06

Kerberoasting, in a Windows domain

This one leaves VulnShop behind for a small Active Directory lab: a domain, an ordinary low-privileged user, and a service account whose password is weak and whose SPN is set. Nothing here is exotic. It is the quiet, ordinary misconfiguration that turns a foothold into a domain.

DDeconstruct

The learner needs a working picture of Kerberos service tickets: any domain user can ask for a ticket to a service, and part of that ticket is encrypted with the service account's own password hash. The holding question falls out of that fact. If anyone is allowed to request the ticket, what is stopping you from taking it away and cracking it offline, on your own time, where no one is watching?

AAttack

I enumerate the accounts that have SPNs, request a ticket for one, and crack its weak password offline. The learner repeats against a different SPN, then reasons about why a long random password would have defeated the whole thing. Success is explaining the offline-crack step and why it is unstoppable once you hold the ticket, not just running the tool that automates it.

RRemediate

The patched service account uses a long random password, or a group-managed service account. The learner requests the very same ticket, runs the very same crack, and it grinds to nothing. Same request, uncrackable ticket. A pentester is supposed to fail, and this failure is a password policy doing its job.

EExchange

On the domain controller, one account requesting a burst of service tickets it has no reason to touch is a distinct, logged event. The learner sees their careful offline attack from the defender's side, where it was noisy the moment it began, and works out how an attacker would slow the requests down to blend in.

Use case 07

SSRF to cloud metadata, in a hosted app

A cloud-hosted version of the app has a feature that fetches a URL you give it, an image importer. That fetch can reach the instance metadata service, the link-local address a cloud machine queries to learn its own configuration, including its temporary credentials. Two ordinary things, dangerous only when they meet.

DDeconstruct

The learner needs both halves before they connect them: what the metadata endpoint is and why it hands out credentials, and what SSRF is, making a server fetch a URL the attacker chose. The holding question is what happens when those two meet. If you can make the app fetch any URL, what comes back when the URL you choose is the metadata service?

AAttack

I use the importer to fetch the metadata endpoint, then walk it down to the role credentials sitting behind it. The learner repeats through a different SSRF sink, then reasons about exactly what those credentials unlock in the account. Success is explaining the pivot, from a web bug to a cloud identity, not just seeing the credentials print.

RRemediate

The patched instance requires a session token for metadata (IMDSv2), limits outbound traffic, and validates the importer's input. The same SSRF now reaches nothing. Same attack, a dead end. That dead end is the fix, and it is worth sitting with, because nothing about the web request changed, only what the environment allowed it to touch.

EExchange

The cloud audit log tells the other half of the story: the role's credentials being used from somewhere they never should be. The learner, freshly out of the attacker's seat, works out what a defender would correlate between the application logs and the cloud audit trail to catch the pivot in progress.

Use case 08

ARP spoofing, on a flat network

A lab network with a client, a gateway, and an attacker on the same segment. No web application at all this time, just the wire everyone assumes is trustworthy. It is a useful reminder that DARE is about understanding systems, and a network is a system like any other.

DDeconstruct

The learner needs to know how a switch and ARP decide where a frame goes, and the uncomfortable fact underneath it: ARP has no authentication, so a host simply believes the most recent reply about who owns an IP. The holding question writes itself. If you can lie about which machine owns the gateway's address, whose traffic starts flowing through you?

AAttack

I poison the client and the gateway so their traffic routes through my machine, then pull a plaintext credential straight out of the captured stream. The learner repeats and captures a different protocol. Success is explaining why the switch cooperated so willingly, that nothing was broken, the protocol did exactly what it was designed to do.

RRemediate

With dynamic ARP inspection in place and every sensitive service over TLS, the same poisoning is either dropped or the captured traffic is unreadable. The attack still runs. It just yields nothing usable. That nothing is the point, and it is a cleaner lesson about encryption than any slide about it.

EExchange

From the defender's side, a flood of unsolicited ARP replies and a MAC address suddenly claiming to be the gateway is a loud, detectable event. The learner, having just been in the middle of the network, can now say precisely what a defender should watch for on the LAN to catch it.

Use case 09

Phishing triage, from the analyst’s seat

This is a defensive session, and it shows how DARE adapts when the learner is a defender. The environment is a reported email sitting in an inbox: headers, a link, an attachment. The four stages still hold. The roles simply start on the other side.

DDeconstruct

The learner needs to know what an email actually is beneath the client: headers that reveal the real origin, a body, and payloads in its links and attachments. The holding question is the analyst's first instinct. The display name says one thing, so what does the header path and envelope actually say about where this came from?

AAttack

Here the “attack” is the investigation. The learner reads the headers, detonates the link and attachment safely in a sandbox, and reaches a verdict backed by evidence. They repeat the whole pass on a second sample, then reason about which indicators were decisive. Success is a verdict they can defend, not a hunch.

RRemediate

Remediate is the response. The learner contains the threat, blocks the sender and URL, pulls the message from every other inbox it reached, then confirms that a re-sent copy no longer lands. The blocked re-delivery is the equivalent of the patched app refusing the payload: proof the fix works.

EExchange

Exchange sends the learner to the attacker's seat. What made this email convincing? What infrastructure sent it? How would you have built it to slip past the very filter that caught it? The analyst who has thought like the sender writes better detections than the one who has only ever received.

Use case 10

Writing a detection, in the SIEM

The environment is a SIEM holding the logs of an attack the learner has already run, the brute force from use case 02 is a good one. The task is not to attack. It is to catch it, reliably, without burying the analyst in false alarms. DARE for the blue team.

DDeconstruct

A detection, stripped down, is a hypothesis about what an attack always leaves behind, written as a query over logs. The learner needs that framing before they write a line. The holding question is the one every good rule answers: what specific, repeatable trace does this attack always produce that ordinary traffic never does?

AAttack

The “attack” here is building the rule. The learner writes a detection from the trace and tunes it against real log data until it catches the attack cleanly. They repeat for a variant of the attack, then reason about the trade between catching everything and crying wolf. Success is explaining why the rule fires when it should.

RRemediate

Remediate inverts into verification. Replay the attack and confirm the rule fires. Then replay a day of benign traffic and confirm it stays silent. A rule that is quiet on normal data matters exactly as much as one that is loud on the attack, and learners feel that the first time their rule screams at nothing.

EExchange

Exchange hands the learner the attacker's seat one more time. How would you change the timing, the volume, or the encoding to slip under the rule you just wrote? Every detection has an evasion. Knowing yours is not a weakness in the rule, it is how you harden it.
