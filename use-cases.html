Four sessions, one target app

Use cases

These are four vulnerability classes run through DARE against the same target, VulnShop, a deliberately vulnerable e-commerce app I use in training. Each one follows the same arc: understand the system, break it, watch it get fixed, then see the break from the other side.

Use case 01

SQL injection, in the search box

VulnShop's product search takes whatever a shopper types and drops it straight into a database query. No parameterization, no escaping. The vulnerable field is the search box on the homepage, which is about as ordinary as an input field gets, and that's the point.

DDeconstruct

Before any injection happens, the learner needs to be able to explain what a database query actually is and how their search term becomes part of the command sent to the database, rather than staying separate from it. I sketch it as one string: the app's fixed code plus whatever the shopper typed, concatenated together and executed as-is. By the end of this stage the learner should be asking themselves what happens if the text they type stops behaving like text.

AAttack

I type ' OR '1'='1 into the search box and the result set jumps from a handful of matching products to the entire catalog, including items that were never meant to be listed. The learner repeats this on the same target, then moves to an independent target where the injectable field is different, the account settings page instead of search, so copying my exact string does nothing. A learner who understood Deconstruct can explain why the quote character breaks the query. One who didn't can only tell you that the string worked.

RRemediate

The one and only change in the patched version is that the query is now parameterized, the search term is passed as data instead of being pasted into the command. Same search box, same payload, and it now returns zero results, exactly like searching for a product that doesn't exist. That is the correct behavior, and I say so directly.

EExchange

I pull up the request log generated by the learner's own search and let them read it before I explain anything. What jumps out is how plainly the injected syntax sits there in a single log line, quote marks and all, next to a thousand ordinary searches for shoes and phone cases. Most learners expect an attack to look more deliberate from the defender's side. Seeing it as one slightly odd-looking line in a wall of normal traffic is usually the moment this stage is built for.

Use case 02

No rate limiting, on the login form

VulnShop's login form accepts as many attempts as you want to throw at it, no delay, no lockout, no captcha after a threshold. The target is the login form, tested with Burp Suite's Intruder against a list of common passwords.

DDeconstruct

The learner needs to understand what a login request actually is, a small package of credentials sent to a server, and what a tool like Intruder does to it: replaying that package with a different guess in the password field each time, as fast as the server allows. I usually capture one manual login first and show the same request sitting in Burp, so the jump from "one login" to "a thousand automated logins" is visible rather than abstract.

AAttack

I run Intruder against the login form with a common password list and narrate what I'm watching for, a response that's a different length or status code than all the failed attempts around it. The learner repeats the run, then moves to an independent target, the password reset form instead of login, which takes the same unlimited-attempts idea and applies it somewhere they haven't seen it demonstrated. That's what separates recognizing the pattern from replaying a recording.

RRemediate

The single change is a lockout after a small number of failed attempts from the same account. Same password list, same Intruder run, and it now stalls a few attempts in, well short of the real password. I point at exactly where it stops and explain that this is the account protecting itself.

EExchange

The evidence here is loud in a way SQL injection isn't: a burst of failed login attempts from a single source, landing within seconds of each other. I show the learner the raw timing between requests before saying a word. It's usually the first time they've thought about how obviously mechanical automated traffic looks once you're the one watching it arrive.

Use case 03

IDOR, in the order history

VulnShop's order confirmation page loads an order by its ID straight from the URL, and never checks whether the order belongs to whoever is asking. The target is the order history page, where order IDs are sequential integers.

DDeconstruct

Before touching anything, the learner needs to understand what an object reference is, a value in a URL, like an order ID, that points directly at a specific record on the server. I show them a real order URL and ask what they think happens if that number changes. That question is the entire point of this stage, and I don't answer it for them yet.

AAttack

I change the order ID in the URL by one and a different customer's order appears, full name, address, items purchased. The learner repeats it on the same target, then moves to an independent target with a different ID pattern, account settings instead of orders, so they have to recognize that "sequential ID, no ownership check" is the actual vulnerability, not "this one URL."

RRemediate

The one change is a server-side check that the requested order actually belongs to the session asking for it. Same incremented ID, same request, and it now returns a not-found response instead of someone else's data. I make the point that the ID being guessable was never the real problem, the missing check was.

EExchange

The logs show a single session requesting a run of sequential order IDs that don't belong to it, one after another. Laid out in a request log, that pattern is about as subtle as a shopping cart on fire. I ask the learner to describe what they see before I point out what makes it stand out, and by then most of them have already spotted it themselves.

Use case 04

Stored XSS, in a product review

VulnShop lets shoppers leave a written review under any product, and renders that text back to every visitor who views the page without encoding it first. The target is the product review field, and the payoff is a stolen session cookie.

DDeconstruct

The learner needs a working sense of two things: what JavaScript running in someone else's browser can actually do, and what a session cookie is worth to someone who gets hold of it. I sketch the flow as one sentence: whatever gets stored in this field gets rendered back to the next person who loads this page. That sentence is what makes stored XSS click before anyone has written a payload.

AAttack

I post a review containing a script that sends the viewing browser's cookie to a listener I control, then open the product page in a second, victim browser session and watch that cookie arrive. The learner repeats it, then moves to an independent target, a profile bio field instead of a review, so they have to recognize "stored input, rendered unescaped" as the pattern rather than reuse my exact payload.

RRemediate

The one change is that stored input is now encoded before it's rendered back into the page. The same review, posted the same way, now shows up on screen as plain, inert text, angle brackets and all, instead of running as code. I point out that the review still saved successfully, it just isn't allowed to act like a program anymore.

EExchange

The evidence is the listener's own log: a request arriving from the victim's browser, carrying their exact cookie value, timestamped to the second they loaded the product page. I let the learner sit with that before explaining it, because it's usually the first time they've seen their own payload act on a browser that isn't theirs.
